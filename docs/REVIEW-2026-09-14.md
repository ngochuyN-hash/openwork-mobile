  (dormant as documented).
- ⚠️ **PARTIAL (most impactful finding in this repo)** — v4.1.5's full-frame gate
  **breaks the GDI fallback path**. The two capture paths disagree on what
  `shotDims` means: on DXGI the daemon reports the **delivery size** (downscaled
  to viewer width — screen.js:249-252, so frames pass the 95% gate); on GDI the
  bridge sets `shotDims = {m.w, m.h}` = the **native** capture size
  (`onWorkerMessage`, screen.js:356-359) while `pumpEncode` shrinks every frame
  to viewer width (880×550-ish, screen.js:404-418). The web gates the first frame
  at ≥95% of the meta-declared shot dims (`web/src/lib/fullframe.js`, wired at
  screen.jsx:309-317, 340-361) — so **every GDI frame is classified as a crop and
  dropped; the GDI path can render nothing** (black stage, fps badge counting),
  exactly the failure class this project fought on 13/09. It also contradicts the
  documented promise "worst case is v3.2 behavior". The replay cache worsens it:
  on GDI every encoded frame lands in `lastJpegByParams` ungated (screen.js:422-423)
  while the DXGI path gates (screen.js:286-290) — and an 880-px replay can never
  pass a 2880-px gate anyway. Reachable: any VM/RDP/compile-fail/driverless box,
  and mid-session daemon death (screen.js:264-272). Fix direction (review only —
  nothing changed): make GDI broadcast the delivered size (or otherwise align the
  two paths) so the gate has a target the frames can actually satisfy.
- ⚠️ PARTIAL (cosmetic) — "old/new cursor area union": `desktop-capture.cs:622-623`
  overwrites `lastCursorX/Y` before `CapturePixels`, so the union at 706-716 only
  covers the NEW cursor box — a stale cursor ghost can persist between keyframes.
